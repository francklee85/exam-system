# 在线考试系统 V1 产品需求文档

## 1. 项目背景

本项目是一个面向职业教育场景的 Web 在线考试系统，主要用于完成专业与班级管理、学生管理、题库管理、试卷管理、考试发布、在线答题、自动评分和成绩查询等基础功能。

系统需要适应职业教育中的实际组织结构。

当前主要专业方向包括：

- 云计算
- AI数媒
- AIGC
- 网络运维

学生按照以下层级进行管理：

专业
→ 班级
→ 学生

例如：

云计算
→ 云计算2501班
→ 张三

V1 版本目标是先实现一个完整、可运行的最小可用版本（MVP），跑通以下核心业务流程：

管理员创建专业和班级
→ 管理员创建教师和学生账号
→ 学生归属到具体班级
→ 教师创建题目
→ 创建试卷
→ 创建并发布考试
→ 指定考试对象
→ 学生登录参加考试
→ 提交答案
→ 系统自动判分
→ 学生和教师查看成绩

V1 不追求功能复杂度，优先保证业务流程完整、数据结构合理、代码结构清晰，并为后续扩展预留空间。

## 3. 用户角色

V1 系统包含三种角色：

### 3.1 管理员

管理员负责系统基础管理。

主要权限：

- 登录系统
- 创建、修改、禁用用户
- 创建和管理专业
- 创建和管理班级
- 创建教师账号
- 创建学生账号
- 为学生分配班级
- 分配用户角色
- 查看用户列表
- 查看考试和成绩基础数据

------

### 3.2 教师

教师负责考试相关业务。

主要权限：

- 登录系统
- 创建和管理题目
- 创建和管理试卷
- 将题目加入试卷
- 设置题目分值
- 创建考试
- 设置考试对象
- 发布考试
- 查看考试状态
- 查看学生考试成绩
- 按专业或班级筛选成绩

------

### 3.3 学生

学生负责参加考试。

主要权限：

- 登录系统
- 查看自己可以参加的考试
- 开始考试
- 在线答题
- 提交试卷
- 查看自己的考试成绩

学生不能查看标准答案和其他学生的考试数据。

当前初始专业包括：

- 云计算
- AI数媒
- AIGC
- 网络运维

专业不能写死在程序代码中，应作为数据库基础数据进行管理。

以后新增专业时，不需要修改代码。

例如：

- 网络安全
- 大数据
- 软件开发
- 鸿蒙开发

都可以直接通过后台新增。

### 4.1 专业基础字段

专业包含：

- 专业名称
- 专业编码
- 专业描述
- 状态
- 创建时间
- 更新时间

例如：

```text
专业名称：云计算
专业编码：CLOUD
状态：启用
```

### 4.2 专业管理功能

## 6. 学生归属关系

每个学生必须归属于一个班级。

通过班级可以确定学生所属专业。

例如：

```text
张三
└── 云计算2501班
    └── 云计算专业
```

推荐的数据关系为：

```text
Student / User
      ↓
    Class
      ↓
    Major
```

学生不需要同时独立保存专业和班级两套归属关系。

建议学生只保存：

```text
class_id
```

专业通过班级关系获取。

这样可以避免出现数据不一致。

例如：

```text
学生班级：云计算2501班
学生专业：AIGC
```

这种错误数据不应该出现。

## 7. 登录与认证

系统支持用户名和密码登录。

登录成功后：

- 后端生成 JWT
- 前端保存认证状态
- 后续 API 请求携带 Token
- 后端根据 JWT 判断当前用户身份
- 根据用户角色控制接口访问权限

系统需要支持：

- 登录
- 获取当前用户信息
- 退出登录
- Token 失效后的重新登录处理

V1 暂不实现：

- 手机号登录
- 邮箱登录
- 第三方 OAuth 登录
- 短信验证码
- 找回密码



## 10. RBAC 权限管理

系统采用 RBAC 角色权限模型。

V1 预定义角色：

- admin
- teacher
- student

V1 可以先使用系统预定义权限，不要求开发复杂的可视化权限配置页面。

系统需要保证：

- 管理员接口不能被教师或学生访问
- 教师业务接口不能被学生访问
- 学生只能访问自己的考试和成绩数据

权限检查必须以后端为准。

前端菜单隐藏不能代替后端权限控制。

## 12. 单选题规则

单选题包含多个选项，例如：

```text
A. Linux
B. Windows
C. macOS
D. Android
```

只能有一个正确答案。

学生只能选择一个选项。

评分规则：

正确：

```text
获得该题全部分值
```

错误：

```text
0 分
```

------

## 13. 多选题规则

多选题包含多个选项。

可以有两个或以上正确答案。

例如：

```text
正确答案：A、C、D
```

V1 评分规则：

只有学生选择的答案和标准答案完全一致时才得分。

以下情况均不得分：

- 少选
- 多选
- 错选

V1 暂不实现部分得分。

答案比较时不受选项顺序影响。

例如：

```text
标准答案：A、C

学生答案：C、A
```

应视为正确。

------

## 14. 判断题规则

判断题只有两个答案：

- 正确
- 错误

答对得分。

答错不得分。

- 创建人

------

## 16. 题目和试卷关系

同一道题可以被不同试卷使用。

同一道题在不同试卷中的分值可以不同。

例如：

```text
题目1001

Linux基础试卷：2分
云计算期末试卷：5分
```

因此：

题目分值应该属于：

```text
试卷与题目的关联关系
```

而不是固定属于题目本身。

------

## 17. 试卷总分

试卷总分由所有试卷题目分值相加得到。

例如：

```text
20道单选题 × 2分 = 40分

10道多选题 × 4分 = 40分

10道判断题 × 2分 = 20分

总分 = 100分
```

系统应该自动计算试卷总分。

不建议教师手工输入总分，避免数据不一致。

## 19. 考试发布

考试在草稿状态时可以修改。

考试发布后，应限制可能影响考试内容的数据修改。

发布考试时，系统需要生成考试试卷快照。

快照至少保存：

- 原题目 ID
- 题干
- 题型
- 选项
- 正确答案
- 答案解析
- 分值
- 题目顺序

例如：

```text
7月22日
教师发布考试

7月23日
教师修改题库中的题目
```

已经发布考试中的原题不能跟着变化。

因此：

```text
Question
   ↓
Paper
   ↓
Exam 发布
   ↓
ExamPaperSnapshot
```

历史考试使用考试快照。

```text

```

该记录称为：

```text

```

例如：

```text
2026年云计算Linux期末考试
```

ExamAttempt 表示某个学生参加某场考试的一次完整答题过程。

例如：

```text
Exam
└── 张三的一次 ExamAttempt
```

记录内容包括：

- 学生
- 考试
- 开始时间
- 提交时间
- 状态
- 得分
- 创建时间
- 更新时间

V1 每个学生每场考试只允许参加一次。

后续版本可以扩展：

- 最大考试次数
- 补考
- 重考
- 取最高分

## 26. 考试倒计时

开始考试后，根据考试时长计算剩余时间。

例如：

考试时长：

```text
60分钟
```

学生：

```text
10:20开始
```

理论结束时间：

```text
11:20
```

但是考试统一结束时间：

```text
11:00
```

实际结束时间应该是：

```text
11:00
```

计算规则：

```text
实际结束时间 =
min(
    开始时间 + 考试时长,
    考试统一结束时间
)
```

前端需要显示倒计时。

后端必须再次校验考试是否超时。

不能只依赖前端倒计时。

------

## 27. 提交考试

学生点击提交后：

1. 前端发送提交请求
2. 后端验证当前用户
3. 后端校验考试状态
4. 后端校验是否超时
5. 锁定本次 ExamAttempt
6. 不允许再次修改答案
7. 系统自动评分
8. 计算最终总分
9. 保存考试成绩
10. 将考试记录状态更新为已提交

提交接口必须防止重复提交。

例如：

- 用户连续点击两次提交
- 网络重试
- 浏览器重复请求

都不能导致重复评分。

------

## 28. 自动评分

V1 三种题型全部支持自动评分。

### 28.1 单选题

学生答案等于正确答案：

```text
得满分
```

否则：

```text
0分
```

### 28.2 多选题

学生答案集合与正确答案集合完全一致：

```text
得满分
```

否则：

```text
0分
```

答案顺序不影响判断。

### 28.3 判断题

学生答案等于正确答案：

```text
得满分
```

否则：

```text
0分
```

## 34. V1 非功能需求

### 34.1 安全性

- 密码必须加密存储，不允许明文保存
- JWT 密钥通过环境变量配置
- 数据库密码通过环境变量配置
- API 必须进行权限校验
- 学生不能通过修改请求参数查看其他学生数据
- 正确答案不能提前返回给学生考试页面

例如学生请求考试题目时：

可以返回：

- 题干
- 题型
- 选项
- 分值

不能返回：

- correct_answer
- 标准答案
- 内部评分字段

------

### 34.2 数据一致性

考试提交和评分过程应使用数据库事务。

必须避免：

- 重复提交导致重复评分
- 修改题库后影响历史考试
- 修改试卷后影响已发布考试
- 删除用户导致成绩记录丢失
- 删除题目导致历史考试无法查看
- 修改班级数据导致历史考试内容变化

------

### 34.3 数据删除原则

对于已经产生业务数据的实体，原则上优先：

- 禁用
- 软删除

而不是直接物理删除。

例如：

已经参加考试的学生不能直接物理删除。

已经被考试使用的试卷不能直接删除。

已经存在班级的专业不能直接删除。

------

### 34.4 可维护性

后端代码应按业务模块划分。

建议模块：

- auth
- users
- roles
- majors
- classes
- questions
- papers
- exams
- attempts
- results

统一：

- API 响应格式
- 异常处理
- 错误码
- 日志格式
- 数据库模型规范
- Pydantic Schema 规范
- 分页格式
- 权限验证方式

------

## 35. 数据库迁移要求

所有数据库结构修改必须使用 Alembic 管理。

禁止开发过程中直接手工修改数据库结构而不记录 Migration。

例如新增：

```text
student_no
```

字段时，应生成对应 Alembic Migration。

## 39. 开发原则

V1 开发遵循以下原则：

1. 优先完成核心业务闭环。
2. 不为暂时不存在的需求过度设计。
3. 先保证数据模型正确，再追求页面美观。
4. 历史考试数据必须保持稳定。
5. 权限控制以后端为最终标准。
6. 前端主要负责展示和用户交互。
7. 核心业务规则必须由后端验证。
8. 所有数据库结构修改统一使用 Alembic。
9. 每完成一个模块后进行测试，再进入下一个模块。
10. 不允许 AI 在需求没有明确说明的情况下自行增加复杂架构。
11. 不为了技术栈完整而提前引入 Redis、MQ、微服务等组件。
12. 优先保证代码清晰、可读、可维护。
13. AI 在开发功能前必须先阅读 docs 目录中的需求和设计文档。
14. 如果需求文档与代码发生冲突，应先指出问题，不允许 AI 擅自修改业务规则。
15. 每次开发尽量只完成一个明确模块，避免一次性让 AI 生成整个系统。
